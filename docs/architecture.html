  • The medical reviewer sees the final text.Humanizer moved before human review, with an automated claim-diff in between — so no wording changes after sign-off.
  • The pipeline now has an ending.Added assembly, schema markup, CMS publishing, indexing, and a Search Console feedback loop. The old diagram stopped at review.
  • Cluster-level coordination.Ten parallel writers get one shared brief set and a cannibalization check up front, plus a cross-article internal-linking sync point after all drafts land.
  • Compliance is a gate, not an afterthought.Infant formula marketing is regulated (WHO Code + local law). The human gate reviews both medical accuracy and compliance.

The critical path

Quality gates, in order

The order is the point: automated checks catch drift cheaply, the humanizer runs before human eyes, and the human gate — the expensive one — sees exactly what will be published.

GATE 1 Automated Fact-check vs fact sheet Every claim in the draft must trace to a cited line in the research agent's fact sheet. Unsourced claims are stripped or flagged. Fail → back to writer
GATE 2 AI pass Humanizer — style only Rhythm, voice, and readability polish. Claims, numbers, and citations are locked; the pass may not touch them. Constrained, not gating
GATE 3 Automated Claim diff Re-run the fact-check on the humanized text. Confirms the style pass changed wording, not meaning. Fail → revert humanizer edit
GATE 4 · BLOCKING Human Medical + compliance review Licensed reviewer signs off on medical accuracy and WHO Code / local-law compliance. Name and credentials go on the page. Nothing publishes without this
Regulatory note. Infant formula promotion is restricted under the WHO International Code of Marketing of Breast-milk Substitutes and national laws in many target markets. Gate 4 must check claims and framing (no idealizing formula over breastfeeding, no health claims barred in the target market). This is the one failure mode that goes beyond rankings.

Component specification

Layer by layer

L1 Strategy

Cadence: monthly · Owner: SEO lead + Claude

Turns search data into a prioritized brief queue.

  • Keyword research — Ahrefs pulls volumes, difficulty, and SERP features for the infant-feeding space.
  • SERP + competitor scan — Firecrawl + web search map who ranks, their angle, and content gaps.
  • Cluster planner — groups keywords into pillar + spoke clusters with one primary keyword per article.
  • Cannibalization check — every planned article is checked against the live sitemap and prior briefs; overlapping intent merges or gets cut before writing starts.

L2 Knowledge

Cadence: always on · grows with every published article

Two stores with different jobs — don't merge them.

  • Vector KB (Pinecone) — the full archive of old blogs, embedded once and enriched with every new publish. It serves four retrieval jobs:
    • Tone of voice — style exemplars retrieved by the writer agent so new articles read like the existing site.
    • Knowledge / coverage map — "what have we already said about X" for the research agent and the cluster planner's cannibalization check, so new articles extend the archive instead of repeating it.
    • Internal-link targets — semantic search over the archive finds the right existing pages to link from and to during assembly.
    • Approved claims library — claims that already passed Gate 4, reusable without re-review.
  • Trusted corpus — research retrieval limited to an allowlist: WHO, AAP, NIH, PubMed, national health authorities. Elicit for papers, web search restricted to the allowlist for guidance pages. No general-web citations in medical claims.

One guardrail: old blogs are a record of what the site has said — not automatically a trusted medical source. A medical claim found only in an old post still needs a trusted-corpus citation (or an approved-claims entry) before it goes in a new draft; otherwise an old unverified claim propagates forever.

L3 Production

Cadence: per cluster · ×10 article agents in parallel

Research is separated from writing so every claim has a paper trail before drafting begins.

  • Brief builder — one brief per article: primary keyword, intent, outline, target internal links, word range, angle vs competitors.
  • Research agent — produces a fact sheet: each claim on its own line with source, publication date, and quote. This is the contract the fact-check gate enforces.
  • Writer agent — drafts from brief + fact sheet + tone retrieved from the vector KB. May not introduce claims absent from the fact sheet.
  • SEO pass — Surfer SEO (or an internal scorer) tunes headings, entity coverage, meta title/description, and image alt text.

L5 Assembly — the cluster sync point

Cadence: once all 10 articles clear Gate 4
  • Internal linking — links woven across the 10 new articles and into existing site pages (targets found by semantic search over the vector KB), spokes to pillar and back. This can only run after all drafts exist — it is the one deliberate barrier in the pipeline.
  • Infographics — generated per article where the fact sheet supports a visual; descriptive alt text written at generation time.
  • Schema markup — MedicalWebPage or Article, FAQPage where Q&A exists, and Person schema for author and medical reviewer with credentials. Non-negotiable for YMYL.

L6 Publishing

Cadence: per cluster, staggered release optional
  • CMS adapter — one thin interface (create draft, upload media, set schema, publish) so the CMS is swappable. Default target: WordPress REST API; Shopify adapter if the content lives on the store.
  • Indexing — sitemap regenerates on publish; IndexNow ping plus Google Search Console sitemap resubmission.

L7 Feedback

Cadence: weekly monitor · quarterly refresh sweep
  • Performance monitor — GSC API tracks impressions, position, and CTR per article; flags decay (falling position on a previously ranking page) and near-misses (position 5–15, worth a push).
  • Refresh queue — flagged articles re-enter the pipeline as update briefs; medical content also gets a dated re-verification pass so "reviewed on" stays honest.
  • KB enrichment — every published article embeds back into the vector KB, so tone and approved claims compound over time.
E-E-A-T is site infrastructure, not article copy. The pipeline assumes these exist once, site-wide: author bio pages with real credentials, the medical reviewer's byline and license shown on every article, an editorial/review policy page, and "medically reviewed on" dates. Without them, YMYL content underperforms no matter how good the pipeline is.

Execution plan

Build roadmap

Current target: end of Phase 2 — the pipeline stops at review-ready drafts. No auto-publishing for now; Phases 3–4 stay on the roadmap but are deferred until draft production is running well.

  1. Foundation — one draft, end to end Stand up the Pinecone KB (old-blog archive + style guide), the trusted-source allowlist, and the brief → research → write → Gates 1–3 flow for a single article. Prove the fact-sheet contract works. Exit: one draft with attached fact sheet, delivered to the review folder for the medical reviewer.
  2. Cluster scale — ×10 parallel Cluster planner + cannibalization check, 10 parallel writer agents, the claim-diff gate, and an internal-linking plan (a suggested link map delivered alongside the drafts, applied manually at publish time). Exit: one full cluster of drafts (pillar + 9 spokes) with fact sheets, meta tags, and link map — ready for review and manual publishing.
  3. Publish automation — deferred CMS adapter, infographic generation, schema templating, sitemap + IndexNow on publish. Picked up once the team trusts the drafts. Exit: approval in Gate 4 is the last manual touch before live.
  4. Feedback loop — deferred GSC monitor, decay + near-miss flagging, refresh queue feeding back into the calendar, KB enrichment from published articles. Exit: the engine proposes its own next month of work.

Still open

Decisions to make

  • CMS platform. WordPress or Shopify (or headless)? Determines the adapter, schema injection method, and where author pages live. Recommendation: WordPress for a content-led site; only Shopify if articles must live on the store domain.
  • Orchestration host — decided. The pipeline runs in the Claude Code desktop app, operated by the SEO manager. The whole cluster run is packaged as custom skills, so operating it means typing /run-cluster weaning schedules — no terminal, no code. Writers and the medical reviewer work in Claude Desktop Projects connected to the same Pinecone KB and MCP servers (single-article work, brief refinement, Gate 4 review with the fact sheet attached). Move to an Agent SDK app with a review dashboard only when volume outgrows one operator.
  • Medical reviewer sourcing. Staff, contracted pediatric RD/RN, or review service. Affects throughput — Gate 4 is the pipeline's rate limiter. Budget reviewer hours per cluster, not per article.
  • Humanizer scope. Keep as a style pass (recommended) — Google targets unhelpfulness, not AI authorship. Drop any "detector evasion" framing; the E-E-A-T layer is what actually protects the site.
  • Target markets. Which countries the site serves determines which formula-marketing laws Gate 4 checks against — and whether an hreflang layer is needed later.
